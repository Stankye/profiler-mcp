# vtune-cli

## Summary
Collection. The CLI syntax is `vtune -collect <analysis_type> [options] [--] <target>` (vtune replaced amplxe-cl starting with the 2019/2020 rebrand; amplxe-cl is the legacy name). Predefined analysis types documented in the 2024.1 User Guide "Run Command Line Analysis" page: performance-snapshot, hotspots, anomaly-detection (preview), threading, hpc-performance, memory-consumption, uarch-exploration (formerly general-exploration), memory-access, sgx-hotspots (deprecated), tsx-exploration (deprecated), tsx-hotspots (deprecated), gpu-hotspots, gpu-offload, graphics-rendering (preview), npu (preview, newer releases), fpga-interaction, io, system-overview. Custom collections use `-collect-with runsa` (PMU counter overflow) or `-collect-with runss` (software sampling). Enumerate at runtime with `vtune -help collect` and per-type knobs with `vtune -help collect <type>` — this is the right way for an automation layer to discover knobs, since they vary by version/platform. Key hotspots knobs: sampling-mode=sw (default, user-mode sampling) vs sampling-mode=hw (hardware event-based sampling; replaced advanced-hotspots in 2019), enable-stack-collection, stack-size, sampling-interval, enable-characterization-insights. Key generic options: -knob name=value (repeatable), -duration=<sec|unlimited> (REQUIRED for system-wide collection, i.e., when no target is given), -target-pid / -target-process (attach), -app-working-dir, -result-dir|-r, -data-limit=<MB> (default 500, 0 = unlimited; alternate -ring-buffer=<sec>), -finalization-mode=full|fast|deferred|none (default fast), -search-dir, -user-data-dir (base dir for result paths), -quiet, -verbose, -start-paused/-resume-after, -allow-multiple-runs, -analyze-system, -no-follow-child, -trace-mpi, -return-app-exitcode.

Reporting. `vtune -report <report_type> -result-dir <result_path> [report_options]`; `-R` is the documented short form of -report and `-r` of -result-dir, so `vtune -R hotspots -r r000hs` is valid. You cannot combine -collect and -report in one invocation. Report types (2024.1): affinity, callstacks, exec-query, gprof-cc, hotspots, hw-events, platform-power-analysis, summary, timeline, top-down, vectspots (plus a Difference report and GPU Compute/Media Hotspots report documented separately; the report types available depend on the analysis type of the result). Discover with `vtune -help report` and `vtune -help report <type>`. Output: text to stdout by default; save with `-report-output <path/file.ext>`, choose CSV with `-format csv -csv-delimiter comma` (tab etc. also accepted), wrap text with `-report-width N`. Filtering/grouping: `-group-by` (multi-level, comma-separated, no spaces; list groupings via -help report <type>), `-sort-asc`/`-sort-desc` (up to 3 fields), `-filter <unit>=<value>` or `!=` where unit ∈ {basic-block, frame, function, function-sync-obj, module, process, source-file, source-line, sync-obj, task, thread, computing-task, computing-instance} (multiple -filter: OR within same column, AND across columns; `-filter=?` lists available filters), `-call-stack-mode all|user-only|user-plus-one`, `-column <substring>` (`column=?` lists columns), `-time-filter <begin>:<end>` in elapsed seconds, and `-limit` (row-count cap, listed in the CLI reference). If -result-dir is omitted for a report, VTune silently uses the highest-numbered compatible result in the CWD — always pass -r in automation.

Results & finalization. Default result dirs are created in the CWD named r<NNN><code>, auto-incremented per analysis type: r000hs (first hotspots), r001tr (threading), r001ue (uarch/Microarchitecture Exploration), r000ps (performance-snapshot), r000ge (legacy general-exploration). Passing `-result-dir=/some/path/` keeps default naming under that path; passing a name creates that exact dir. The directory contains the raw data plus a *.vtune project file openable in the GUI. Finalization (symbol resolution/DB build) runs automatically after collection; -finalization-mode=fast is the default (reduced samples), full is most accurate, deferred computes only binary checksums so you can finalize on another machine (IoT/embedded use case), none skips it. Re-finalize anytime with the `-finalize` action plus -result-dir (and -search-dir for binaries/symbols).

Platforms, drivers, scripting. Current system requirements (2025.1): 64-bit Linux and Windows hosts/targets only; FreeBSD 12/13, Android, QNX as targets; "No macOS supported" — macOS (which only ever supported viewing results, never native collection) was deprecated and discontinued after the 2023.1 release (gone in 2024.0); Intel points macOS users at VTune Profiler Server's web UI. Hardware event-based sampling uses either the Intel sampling driver (SEP, requires admin to install) or driverless Linux perf collection (kernel 4.18–6.11 per 2025.1 reqs). Driverless prerequisites: /proc/sys/kernel/perf_event_paranoid <= 1 for per-process profiling, = 0 for system-wide and uncore events (Memory Access analysis requires uncore and will not run without it); other pitfalls: file-descriptor limits (ulimit -n) for uarch-exploration's long event lists, perf_event_mlock_kb (default 518KB) for multi-process, NMI watchdog contention, 1024-byte default stack size for stack unwinding (raise via -knob stack-size). Since VTune Amplifier 2019 U4, stack collection always uses driverless mode even when SEP is loaded. The Summary "Collection and Platform Info" section records which collector (Perf vs SEP) was used. The self-check script <install-dir>/bin64/vtune-self-checker.sh runs representative analyses and reports pass/fail, limitations, and remediation; --log-dir sets the log location (useful under job schedulers). Exit codes: by default vtune returns its own exit code (0 success, non-zero failure — no numeric table is published); `-return-app-exitcode` (collect only) makes it return the target's exit code instead; reports go to stdout, diagnostics to stderr; -quiet suppresses non-essential messages. Install: standalone or oneAPI Base Toolkit; defaults /opt/intel/oneapi/ (root) or $HOME/intel/oneapi/ (non-root) on Linux, C:\Program Files (x86)\Intel\oneAPI\ on Windows; set environment with `source /opt/intel/oneapi/vtune/latest/env/vars.sh` (modern layout; the legacy script name is vtune-vars.sh in the vtune install root, and the toolkit-wide setvars.sh also works).

## Key facts
- -collect analysis types (2024.1): performance-snapshot, hotspots, anomaly-detection (preview), threading, hpc-performance, memory-consumption, uarch-exploration (former general-exploration), memory-access, sgx-hotspots (deprecated), tsx-exploration (deprecated), tsx-hotspots (deprecated), gpu-hotspots, gpu-offload, graphics-rendering (preview), npu (preview), fpga-interaction, io, system-overview; custom via -collect-with runsa|runss
- Hotspots knobs: sampling-mode=sw (default) | hw, enable-stack-collection, stack-size, sampling-interval, enable-characterization-insights; enumerate with 'vtune -help collect hotspots'
- -report types (2024.1): affinity, callstacks, exec-query, gprof-cc, hotspots, hw-events, platform-power-analysis, summary, timeline, top-down, vectspots (+ Difference and GPU Compute/Media Hotspots reports); available types depend on the result's analysis type
- -R is the short form of -report; -r is the short form of -result-dir; collect and report actions cannot be combined in one command
- Report formatting: default text to stdout; -report-output <file>, -format csv -csv-delimiter comma, -report-width <N>
- Filtering/grouping: -group-by (comma-separated levels), -sort-asc/-sort-desc (up to 3 fields), -filter <unit>=<value>|!= (units: basic-block, frame, function, function-sync-obj, module, process, source-file, source-line, sync-obj, task, thread, computing-task, computing-instance), -call-stack-mode all|user-only|user-plus-one, -column <substring>, -time-filter begin:end, -limit; introspection via -filter=? and column=?
- Result dirs auto-named r<NNN><analysis-code> in CWD (r000hs first hotspots, r001tr threading, r001ue uarch-exploration, r000ps performance-snapshot); contains a .vtune project file; report without -r uses highest-numbered compatible result in CWD
- -finalization-mode=full|fast|deferred|none, default fast; deferred computes binary checksums only for finalization on another machine; re-finalize with the -finalize action + -result-dir
- -duration=<seconds|unlimited> is required for system-wide collection (no target specified); -data-limit=<MB> default 500, 0 = unlimited (alternate: -ring-buffer=<sec>)
- -return-app-exitcode (collect only) returns the target's exit code instead of vtune's own; default is vtune's exit code; no numeric exit-code table is published in the docs
- Platform support (2025.1 system requirements): 64-bit Linux and Windows hosts/targets; FreeBSD 12/13 targets; 'No macOS supported' — macOS (viewer-only, never native collection) deprecated and discontinued after 2023.1, removed in 2024.0; VTune Profiler Server web UI is the macOS viewing alternative
- Driverless perf collection requires perf_event_paranoid <= 1 (per-process) or = 0 (system-wide/uncore); Memory Access analysis requires uncore events and will not run without them; kernel 4.18-6.11 supported for EBS/driverless per 2025.1
- Since VTune Amplifier 2019 U4, stack collection (enable-stack-collection) always uses driverless perf mode even when the Intel SEP sampling driver is loaded; SEP driver install requires admin privileges
- Self-check: <install-dir>/bin64/vtune-self-checker.sh runs representative analyses (hotspots sw/hw±stacks, threading, hpc-performance, uarch-exploration, memory-access with uncore, performance-snapshot, GPU hotspots) and reports failures, limitations, and fixes; --log-dir sets log location
- Install paths: Linux /opt/intel/oneapi/ (root) or $HOME/intel/oneapi/ (non-root); Windows C:\Program Files (x86)\Intel\oneAPI\; env setup: source /opt/intel/oneapi/vtune/latest/env/vars.sh (or toolkit-wide setvars.sh; legacy name vtune-vars.sh)
- CLI reference option list (2024.1): allow-multiple-runs, analyze-system, app-working-dir, archive, call-stack-mode, collect, collect-with, column, command, cpu-mask, csv-delimiter, cumulative-threshold-percent, custom-collector, data-limit, discard-raw-data, duration, filter, finalization-mode, finalize, format, group-by, help, import, inline-mode, knob, limit, loop-mode, no-follow-child, no-summary, quiet, report, report-knob, report-output, report-width, result-dir, resume-after, return-app-exitcode, ring-buffer, search-dir, show-as, sort-asc, sort-desc, source-object, source-search-dir, stack-size, start-paused, strategy, target-pid, target-process, time-filter, trace-mpi, user-data-dir, verbose, version

    vtune -collect hotspots -knob sampling-mode=hw -duration=20
    vtune -collect threading -duration=60 -- /home/test/sample
    vtune -collect hotspots -data-limit=200 myApp
    vtune -collect hotspots -knob sampling-mode=hw -finalization-mode=deferred -- C:\test\myApp.exe
    vtune -collect hotspots -result-dir=/home/test/ -- /home/test/myApplication
    vtune -collect hotspots -knob sampling-mode=hw --target-pid 377
    vtune -collect hotspots -knob sampling-mode=hw --app-working-dir=/home/<username> -- ffmpeg -y -f lavfi -i testsrc=duration=600:size=1280x720:rate=30 testsrc.mp4
    vtune -collect hotspots -knob sampling-mode=hw -knob enable-stack-collection=true -knob stack-size=2048 <application>
    vtune -collect threading -return-app-exitcode -- /home/test/sample
    vtune -collect-with runsa -knob event-config=<events> -- <target>
    vtune -report hotspots -r r001hs
    vtune -report hotspots -result-dir r001hs -report-output /home/test/MyReport.txt
    vtune -R hotspots -report-output MyReport.csv -format csv -csv-delimiter comma
    vtune -report hw-events -group-by package -r unc
    vtune -report hotspots -report-width 60 -report-output MyHotspotsReport.txt
    vtune -report callstacks -r r001tr -group-by callstack
    vtune -report hotspots -r r002hs -group-by process,process-id,module,function
    vtune -report hw-events -r r001ue -sort-asc INST_RETIRED.ANY,CPU_CLK_UNHALTED.CORE
    vtune -report hotspots -filter module=sample.dll -filter module=sample2.dll
    vtune -report hotspots -filter process!=app
    vtune -report hotspots -group-by function -call-stack-mode user-plus-one
    vtune -R hw-events -r r000hs --column=INST_RETIRED.
    vtune -report hotspots -result-dir r001tr -group-by function -time-filter 1.25:5.0
    vtune -help collect
    vtune -help collect hotspots
    vtune -help report
    vtune -help report hotspots

## Caveats
- This machine is macOS (Darwin): current VTune releases ship no macOS binary at all ('No macOS supported', discontinued after 2023.1), so the automation layer must drive vtune on a remote Linux/Windows host, in a Linux container, or via VTune Profiler Server — it cannot shell out to a local vtune on macOS.
- No numeric exit-code table is documented; only 'vtune exit code by default' vs -return-app-exitcode is specified. Treat 0 as success and non-zero as failure, and parse stderr for diagnostics; verify empirically on your target version.
- If -result-dir/-r is omitted on -report, VTune uses the highest-numbered compatible result in the current working directory — always pass -r explicitly in automation.
- Knob names/values and available analysis types vary by VTune version, OS, and CPU; 'vtune -help collect <type>' / 'vtune -help report <type>' are the authoritative runtime source and should be what the automation layer introspects.
- The -limit (row count) option and the exact result-dir suffix codes beyond hs/tr/ue/ps/ge were taken from the CLI reference index and search snippets, not from pages read in full — verify with 'vtune -help report'.
- Analysis-type status shifts across releases: gpu-hotspots/anomaly-detection/npu/graphics-rendering are (or were) preview; sgx-hotspots and tsx-* are deprecated; uarch-exploration was formerly general-exploration; advanced-hotspots was folded into hotspots -knob sampling-mode=hw in 2019.
- The -knob option must precede the analysis target on the command line, and Intel docs use both '-option value' and '-option=value' plus double-dash GNU-style forms interchangeably; the '--' separator before the target application is required whenever the target takes its own arguments.
- The legacy env script name vtune-vars.sh (in the vtune install root) appears in older docs; the verified modern path is /opt/intel/oneapi/vtune/latest/env/vars.sh (or the toolkit-wide setvars.sh) — check which exists in your installed version.
- The docs' group-by example contains a typographic en-dash (–group-by); use ASCII hyphens in real commands.
- The macOS discontinuation timing (deprecated after 2023.1, x86 macOS dropped in 2024.0) was corroborated via Intel release-notes/community search snippets rather than a fully read release-notes page; the 2025.1 system-requirements page read directly states 'No macOS* supported'.
