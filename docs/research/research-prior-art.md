# prior-art

## Summary
Prior art exists but is thin, immature, and fragmented — there is real room for a well-designed VTune MCP server. (1) Exactly one VTune MCP project was found: wanggan768q/vtune-mcp-server (Python 3.10+, single-file server.py wrapping the VTune 2026.1 CLI, listed on Glama). It exposes six tools — vtune_report, vtune_list_results, vtune_compare, vtune_summary, vtune_hotspots (top-N CSV), vtune_function_tree (interactive HTML diff report with collapsible call trees and red/green deltas written to the filesystem) — but has 0 stars, 6 commits, one contributor, and no license, so it is prior art to learn from rather than a competitor or a dependency. (2) The nearest analogues in other profiler ecosystems: KorovkoAlexander/nsys_profiler_mcp (NVIDIA Nsight Systems; 10 tools incl. check_nsys, profile_binary, load_report/list_reports, get_kernel_stats/get_nvtx_stats/get_memcpy_stats, build_interval_tree/query_interval_tree; MIT; note the GitHub URL 404'd on direct fetch — possibly renamed/removed, details verified via its Glama mirror), Sarthak160/Profiler-MCP (Go pprof + Python cProfile + Java JFR; just two tools: analyze_profile and open_interactive_ui which spins up a localhost pprof flamegraph server), antarikshc/perfetto-mcp (13 tools over trace_processor PerfettoSQL, incl. an execute_sql_query escape hatch; Apache-2.0), and jamesrochabrun/XcodeTraceMCP (Instruments/xctrace; profile_running_app, analyze_trace, compare_traces with a failOnRegression flag, cleanup_traces, plus check_xctrace/list_templates/list_devices discovery tools; MIT; TypeScript). No dedicated MCP servers were found for linux perf, py-spy, samply, magic-trace, or speedscope; Google's official chrome-devtools MCP covers browser tracing (performance_start_trace/stop_trace/performance_analyze_insight). So the profiler-MCP space is essentially one hobby project per profiler.

(3) Tool-surface design converges on the same patterns everywhere: never return raw profile data — return aggregated, structured summaries (perfetto-mcp returns JSON with Summary/Details/Metadata sections; nsys-mcp aggregates kernel stats with mean/std/min/max/median/count/total). Token capping is done via top_n parameters (nsys get_kernel_stats, vtune_hotspots), limit/filter parameters (perfetto find_slices), and bounded recording duration (XcodeTraceMCP's XCTRACE_ANALYZER_MAX_DURATION_SECONDS=300); Anthropic's "Writing effective tools for agents" post adds the concrete guidance: Claude Code truncates tool responses at 25k tokens by default, so implement pagination/filtering/truncation with sensible defaults, offer a response_format concise-vs-detailed enum (their Slack example: 206 -> 72 tokens), and return actionable errors instead of tracebacks. Notably, NONE of these servers use actual MCP resources — they all persist results server-side and hand the LLM handles: nsys-mcp has a two-tier cache (in-memory LRU of 8 loaded reports + disk at ~/.nsys_mcp/cache/, keys derived from binary path + args so identical profiling runs are never re-run) with list_reports/load_report tools; vtune-mcp uses VTune result directories on disk plus vtune_list_results; human-facing visualization is delivered as HTML files on disk or a localhost web UI URL, never inlined to the model. perfetto-mcp's execape hatch — curated high-level tools (detect_jank_frames, anr_root_cause_analyzer) plus one raw execute_sql_query tool — is the strongest drill-down design and maps well to VTune (whose result dirs are SQLite-backed and whose CLI supports filtered CSV reports).

(4) Agentic profiling loops: the canonical reference is AMDResearch/intelliperf (MIT, CLI not MCP): profile with rocprofiler-compute -> identify bottleneck class via "Guided Tuning" formulas (bank conflicts, memory access patterns, atomic contention, or diagnose-only) -> pinpoint source lines with Omniprobe instrumentation -> LLM generates optimized code -> Accordo re-runs and validates BOTH correctness (output comparison with tolerance) and performance delta, iterating with feedback. The PRAGMA paper (arXiv 2511.06345) validates the core premise quantitatively: feeding fine-grained hardware profiling data into the LLM reasoning loop (vs. correctness/wall-time-only feedback) yields 2.81x/2.30x average speedups over Torch on KernelBench CPU/GPU, and it preserves historical best versions across iterations. XcodeTraceMCP operationalizes the loop endpoint as a tool: compare_traces takes baseline+current, reports function-level deltas, and can hard-fail the MCP call when failOnRegression is set — giving the agent an unambiguous termination/rollback signal. vtune_compare + vtune_function_tree in the existing VTune server serve the same diff role. Takeaway: a first-class diff/compare tool with machine-checkable pass/fail, plus separate correctness validation, is what turns a profiler wrapper into an agentic optimization loop.

(5) Eval/self-test harnesses: only XcodeTraceMCP ships its own (pnpm verify, test:integration against real xctrace, test:mcp-smoke for stdio protocol testing) — every other profiler MCP ships none, so a built-in eval harness is a genuine differentiator. Generic frameworks to build on: lastmile-ai/mcp-eval (pip install mcpevals; runs a real LLM agent against your real server rather than mocking), mclenhard/mcp-evals (Node package + GitHub Action, LLM-graded scoring from YAML/TS configs), Kylejeong2/mcpvals (deterministic metrics + full MCP spec coverage incl. resources/prompts), plus benchmarks MCP-Bench (Accenture) and MCP-Universe. Anthropic's tools post prescribes the methodology: realistic multi-step eval tasks, measuring accuracy, runtime, tool-call count, and token consumption, then letting the agent analyze its own transcripts to improve tool definitions.

## Key facts
- Only existing VTune MCP: github.com/wanggan768q/vtune-mcp-server — Python 3.10+, 6 tools (vtune_report, vtune_list_results, vtune_compare, vtune_summary, vtune_hotspots, vtune_function_tree), 0 stars, 6 commits, NO license, requires VTune 2026.1, VTUNE_PROJECT_DIR env var for path shorthand, writes interactive HTML call-tree diff reports to disk
- nsys-mcp (KorovkoAlexander/nsys_profiler_mcp, MIT, Python/FastMCP): 10 tools — check_nsys, profile_binary, load_report, list_reports, get_event_summary, get_kernel_stats (top_n param), get_nvtx_stats, get_memcpy_stats, build_interval_tree, query_interval_tree (query types: most_time_consuming, top_level, count_calls, subtree_summary, with max_depth); two-tier cache: in-memory LRU max 8 reports + disk at ~/.nsys_mcp/cache/ keyed by binary path + args so identical runs skip re-profiling
- perfetto-mcp (antarikshc/perfetto-mcp, Apache-2.0, Python 3.13+): 13 tools over trace_processor — find_slices, execute_sql_query (raw PerfettoSQL escape hatch), detect_anrs, anr_root_cause_analyzer, cpu_utilization_profiler, main_thread_hotspot_slices, detect_jank_frames, frame_performance_summary, thread_contention_analyzer, binder_transaction_profiler, memory_leak_detector, heap_dominator_tree_analyzer; all tools return structured JSON with Summary/Details/Metadata sections
- XcodeTraceMCP (jamesrochabrun/XcodeTraceMCP, MIT, TypeScript/Node 18+): tools profile_running_app, track_running_app, analyze_trace, compare_traces (baseline vs current function-level deltas, failOnRegression flag fails the MCP call), cleanup_traces, list_templates, list_devices, check_xctrace; bounds trace size via XCTRACE_ANALYZER_MAX_DURATION_SECONDS (default 300); ships its own test harness: pnpm verify, test:integration, test:mcp-smoke (stdio protocol smoke test)
- Sarthak160/Profiler-MCP (Go): only 2 tools — analyze_profile (pprof/cProfile/JFR summaries of hot paths, not raw dumps) and open_interactive_ui (launches background pprof web server, returns localhost URL for human flamegraph inspection); auto-executes .py with cProfile and .jar with a fixed 60s JFR recording
- No dedicated MCP servers found for linux perf, py-spy, samply, magic-trace, or speedscope (as of 2026-07); browser tracing is covered by Google's official chrome-devtools MCP (performance_start_trace / performance_stop_trace / performance_analyze_insight)
- AMDResearch/intelliperf (MIT, CLI not MCP): full agentic loop — rocprofiler-compute profiling -> Guided Tuning bottleneck formulas (bankConflict, memoryAccess, atomicContention, diagnoseOnly) -> Omniprobe source-line attribution -> LLM codegen (--provider/--model, default GPT-4o) -> Accordo validates correctness (output diff w/ tolerance) AND performance before accepting
- PRAGMA paper (arXiv 2511.06345): putting hardware profiling data in the LLM reasoning loop (vs correctness/runtime-only feedback) gives 2.81x CPU / 2.30x GPU average speedup over Torch on KernelBench; also preserves historical best code versions across iterations
- Anthropic 'Writing effective tools for agents': Claude Code truncates tool responses at 25k tokens by default; recommend pagination/filtering/truncation with sensible defaults, a response_format concise|detailed enum param (their example cut 206 -> 72 tokens), natural-language identifiers over UUIDs, namespaced tool prefixes, actionable error messages, and eval-driven tool iteration measuring accuracy/runtime/tool-calls/token-use
- None of the surveyed profiler MCPs expose results as MCP resources — all persist server-side (disk cache / result dirs) and return handles (report IDs, paths, localhost URLs) via tools; HTML/flamegraph visualizations go to the filesystem or a local web server for humans, never into model context
- MCP eval frameworks: lastmile-ai/mcp-eval (pip install mcpevals; real agent against real server, no mocks), mclenhard/mcp-evals (Node + GitHub Action, LLM-graded), Kylejeong2/mcpvals (deterministic metrics, full spec coverage), Accenture/mcp-bench and MCP-Universe (benchmarks); only XcodeTraceMCP among profiler MCPs ships self-tests

## Example commands
    claude mcp add vtune -e VTUNE_PATH="C:/Program Files (x86)/Intel/oneAPI/vtune/2026.1/bin64/vtune.exe" -- python server.py  # config pattern used by wanggan768q/vtune-mcp-server
    intelliperf [options] -- <profile_cmd>  # IntelliPerf CLI usage pattern: everything after -- is the profiled command
    perf record -F 99 -a -g -- sleep 60  # canonical perf capture; perf script | stackcollapse-perf.pl | flamegraph.pl > out.svg (brendangregg/FlameGraph)
    pnpm test:mcp-smoke  # XcodeTraceMCP's MCP stdio protocol smoke test; also pnpm verify, pnpm test:integration
    pip install mcpevals  # or: uv tool install mcpevals  (lastmile-ai/mcp-eval framework)
    npm install mcp-evals  # mclenhard/mcp-evals, runnable as a GitHub Action with YAML/TS eval configs

## Caveats
- Direct fetch of github.com/KorovkoAlexander/nsys_profiler_mcp returned 404 — the repo may have been renamed, made private, or deleted; all nsys-mcp details were verified via its Glama directory mirror (glama.ai/mcp/servers/KorovkoAlexander/nsys_profiler_mcp), so re-check the canonical URL before citing or depending on it
- wanggan768q/vtune-mcp-server has no license file — its code cannot be legally reused, only its design studied; it is also effectively dead (0 stars, 6 commits, 1 contributor)
- Tool lists and behaviors were taken from READMEs and directory listings, not from reading source code — exact parameter schemas, default limits, and truncation behavior should be verified against source before copying designs
- Search was unable to confirm ANY MCP server exists for linux perf, py-spy, samply, magic-trace, or speedscope; absence of search results is weak evidence of absence — a targeted GitHub code search (e.g. gh search repos) would be more conclusive
- No 'AMD intellikit' was found — the AMD Research project is called IntelliPerf (plus related papers SwizzlePerf arXiv:2508.20258 and the Zenodo record 15845118); if the requester meant a different project, that name yielded nothing
- IntelliPerf and PRAGMA are ROCm-GPU/kernel-focused, not VTune/CPU-focused — their loop architecture transfers but their bottleneck formulas and validation tooling (Omniprobe, Accordo) are AMD-stack-specific
- Profiler-MCP's pattern of implicitly executing user scripts (auto-runs .py under cProfile, .jar under 60s JFR) is a design to AVOID or gate carefully in an MCP server — surprising side effects and fixed durations; prefer explicit profile_binary-style tools with bounded, user-visible parameters
